# Каталог методов VarWar

Каталог разделяет статистические примитивы, настройки и готовые конвейеры.
Сравнивать в одной гонке следует **итоговые конвейеры с одинаковой целевой
величиной**, а не все классы, которые умеет вызвать библиотека.

| Категория | Что делает | Примеры |
| --- | --- | --- |
| `Estimator` | Оценивает эффект и строит статистический вывод | Welch, ML-RATE, стратифицированная оценка |
| `HypothesisTest` | Проверяет гипотезу, но не обязан оценивать эффект | KS, energy test |
| `MetricTransformer` | Преобразует исходное определение метрики | планируемая линеаризация ratio |
| `TargetTransformer` | Меняет target перед оцениванием | CUPED, CUPAC, winsorization |
| `FeatureAdapter` | Меняет представление признаков без использования target | `numeric_feature_binner` |
| `DesignPreprocessor` | Готовит выборку, страты или схему назначения до анализа | `genetic_strata_reducer` |
| `OptimizationObjective` | Задаёт внутреннюю целевую функцию алгоритма | `ab_proportional` |
| `ConfigurationProfile` | Фиксирует интеграционный профиль без нового преобразования данных | будущий профиль HypEx matching |
| `InferenceCorrection` | Корректирует множественный статистический вывод | Holm, Romano-Wolf |
| `CompositePipeline` | Соединяет совместимые компоненты | CUPED → HypEx A/B |

`DesignPreprocessor` не означает автоматически «разбить пользователей на A и
B». Он может построить и заморозить страты, подготовить выборку, сформировать
блоки или выполнить рандомизацию. Конкретный контракт зависит от компонента.

CUPAC A, A+B и A+B+C считаются отдельными `TargetTransformer`-вариантами.
При этом B и C не расширяют набор признаков модели A: это последовательные
линейные корректировки текущего контроля с разными правилами допуска данных.

## Активная граница RCT-гонки

Исполняемая синтетическая гонка сейчас ограничена рандомизированными
экспериментами. Она строится как сравнение полных пайплайнов, а не отдельных
трансформеров. В каждом результате сохраняются два независимых измерения
доступа к информации:

1. `race_information_mode`: `experiment_only` или `panel_prior`;
2. `temporal_mode`: `pre_treatment_only` или `post_treatment_allowed`.

Пайплайны с B/C используют разрешённые in-time зоны и поэтому не должны
смешиваться с pre-treatment-only результатами. Panel-prior пайплайны получают
только агрегированные исторические статистики до отсечения и не получают
строки исторического пула.

Компактные trial-level метрики для аудита включаются в лист `Полные прогоны`,
если размер прогона позволяет сохранить книгу удобной; для больших прогонов
лист содержит пояснение, а полный raw CSV со всеми diagnostics сохраняется
рядом с книгой.
Лист `Dashboard` содержит выпадающие фильтры по информационному режиму,
временному доступу, сценарию, контуру, estimand и семейству запуска и
пересчитывает показатели по достаточным агрегатам: суммам эффекта, квадрата
эффекта, SE, покрытия, FPR, мощности и времени. Поэтому переключение фильтров
не сканирует trial-level строки. Это позволяет сравнивать
одинаковые пайплайны при разном доступе к информации, не выдавая
информационное преимущество за преимущество алгоритма.

Критерий выбора хранится на листе `Выбор лучшего` и в `selection.csv`:
сначала исключаются изменённая метрика, несопоставимые estimand-ы, ошибки
запуска, превышение допусков bias/FPR/coverage/SE и недостаточное число
Monte Carlo повторов; затем победитель выбирается отдельно внутри каждого
сценария × информационного режима × временного режима × estimand по
минимальному эмпирическому SD. Время и ID используются только при равенстве.
Пока минимальный объём повторов не достигнут, победитель намеренно не
выводится.

IV/LATE, ratio-метрики, изменение целевой метрики и observational-сценарии
сохраняются в каталоге, но не входят в активный рейтинг RCT.

## Правило безопасности данных

Основные пайплайны рассчитаны на один доступный датасет. Pre-treatment признаки
и их lag2/lag1 значения допустимы для temporal CUPAC A и подготовки дизайна.
Текущий outcome не должен влиять на обучение A или на замороженную
предобработку дизайна.

In-time признаки допускаются только по явной политике:

- B проходит экспертную причинную проверку до запуска;
- C сначала очищается от outcome-derived, leakage и mediator-risk признаков,
  затем проходит автоматические проверки баланса и пропусков;
- D, требующие отдельного причинного графа, пока не входят в основную гонку;
- E с риском медиаторства и F с утечкой запрещены.

Линейные этапы B/C обучаются только на текущем контроле. Это всё равно требует
эмпирической проверки смещения, FPR и покрытия.
